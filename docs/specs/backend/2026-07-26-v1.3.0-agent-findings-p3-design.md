## 3. #7 后半 shell 命令级策略

### 3.1 现状

- shell 工具无任何命令级过滤;auto/full-auto 档权限矩阵对 `execute` 类别返回 allow([`permission-engine.js:19-28`](../../../src/tools/permissions/permission-engine.js)),模型可执行任意二进制;`argv[0]` 不做路径检查,可直接调用工作区外任意绝对路径。
- test 工具在自身 `execute` 内**直接调用** `createShellTool().execute()`([`test.js:26`](../../../src/tools/builtin/test.js)),实际 argv 从不过权限引擎——引擎层方案对它无效。
- 审批提示 summary 仅为 `"shell requires approval"`([`executor.js:52`](../../../src/tools/executor.js)),用户看不到被批准的命令;但完整 securedCall 已随 `approval:requested` 事件发布(executor.js:55),三端已收到 argv,只差渲染。
- 现成机制:registry.secureToolCall 支持工具级 `resolveCategory(params)` 钩子([`registry.js:39`](../../../src/tools/registry.js),memory 工具有先例);权限矩阵对**未知类别**在所有档位默认 ask(`matrix[category] || "ask"`,permission-engine.js:59);`destructive` 类别在 decide() 最前端硬拒(36-38 行,先于审批缓存,**不可被缓存放行**)。

### 3.2 机制 — 双层

新增 `src/security/command-policy.js`(纯模块、零依赖):

```text
classifyCommand(argv) → "safe" | "dangerous" | "forbidden"
```

**归一化**:取 `argv[0]` basename、小写、剥 `.exe/.cmd/.bat/.com` 后缀,再按规则匹配(部分规则需看 argv 后续参数,如 `git push --force`)。

**第 1 层(权限引擎,经 resolveCategory,引擎零改动):**

- shell 工具新增 `resolveCategory(params)`:`forbidden` → 返回 `"destructive"`(引擎硬拒,且先于审批缓存);`dangerous` → 返回 `"execute_dangerous"`(矩阵未知类别 → **所有档位 ask**,恰好满足「auto 与 full-auto 均升级确认」);`safe` → 返回默认 `"execute"`(行为与现网完全一致)。
- git 工具同样接入:read 白名单操作维持 `"read"`;非 read 操作走 `classifyCommand`(覆盖 `git push --force` 等)。
- 类别参与审批指纹(permission-engine.js:89),5 分钟精确参数缓存语义不变。
- 已知交互:verifier 恢复/初验强制 autonomy `"auto"`(agent-runtime.js:199-211、549、688),但 test 工具嵌套 argv 不过引擎,故验证回路**不会**新增确认;ask-in-verify 由既有 resume 机制支持,无需改动。

**第 2 层(runProcess 兜底,仅禁止类):**

- [`shell-policy.js`](../../../src/security/shell-policy.js) `runProcess` 在 spawn 前调用 `classifyCommand(argv)`,`forbidden` → 返回策略拒绝结果(形状同 `spawnErrorResult`,错误信息注明 policy 拒绝),**不 spawn**。
- 兜底动机:统一覆盖 shell / git / test 嵌套执行及未来任何 runProcess 复用方。`dangerous` **不在此层拦截**(该层在审批机制之下,只能硬拒,无确认 UX;test 嵌套的 `cmd.exe /c npm test` 属包装 shell 归高危,若在此层拦会打断验证回路——外层 test 调用已过引擎,属有意放行)。

### 3.3 内置清单(初稿,实现期可微调,硬编码)

| 类 | 规则 |
|----|------|
| **forbidden** | `format`、`mkfs*`、`diskpart`、`bcdedit`、`dd`(写设备语义) |
| **dangerous** | 直接删除类:`rm`、`rmdir`、`rd`、`del`;系统级:`shutdown`、`reg`、`sc`、`schtasks`、`taskkill`;网络下载执行链常客:`curl`、`wget`(argv-only 无管道,风险在包装 shell 内,此处从宽可讨论);发布类:`npm publish`(argv 含 `publish`)、`git push --force`/`--force-with-lease`/`push --delete`(argv 规则);**包装 shell 一律高危**:`bash`、`sh`、`zsh`、`dash`、`cmd`、`powershell`、`pwsh`;解释器仅带执行参数时高危:`node -e/--eval`、`python -c`、`ruby -e`、`perl -e` |
| **safe** | 其余一切,行为与现网一致 |

> 注:`shell:false` + argv-only 意味着无管道/重定向,`curl \| sh` 类走私只能经包装 shell 发生——包装 shell 整体归高危即为主防线。

### 3.4 审批提示与 argHint 顺手修

1. **summary 加 argv 预览**:executor.js:52 的 summary 改为含截断后的 argv 拼接(如 `` shell requires approval: `git push --force origin main` ``,上限 ~120 字符),三端自动受益;CLI 阻塞式提示只见 summary,是主要受益方。
2. **argHint bug**:[`event-contract.js`](../../../src/apps/event-contract.js) `argHint` 读 `event.call.args`,但执行器发布的是 `call.params`(executor.js:32),且 `ARG_KEYS` 缺 `"argv"`——两处补齐(读 `call.params ?? call.args`;`ARG_KEYS` 增 `argv`,数组值做 join+截断),工具调用卡片参数提示恢复非空。

### 3.5 测试

- `classifyCommand` 单测:归一化(大小写/后缀/basename)、三类清单代表命令、包装 shell、解释器 `-e/-c` 有无、`git push --force` argv 规则、空/异常 argv。
- resolveCategory 接线:shell 工具 forbidden → decide 返回 deny(且审批缓存不可放行);dangerous → 各档位(supervised/gated/auto/full-auto)均 ask;safe → 行为与现网矩阵一致;git 工具 read 操作不受影响。
- runProcess 兜底:forbidden argv 不 spawn、返回策略拒绝结果;dangerous/safe 正常执行;现有 shell/git/test 套件不回归(test 工具 `cmd.exe /c` 嵌套路径仍可跑)。
- summary/argHint:approval summary 含 argv 预览;`describeEvent` 对 `call.params.argv` 产出非空 argHint。
